# QAV250 — проверка BMI270 + BMM150 и MEKF

Проверен предоставленный файл «Вставленный код.c», 1969 строк. Дата проверки: 16 сентября 2026.

Примечание к комплекту репозитория: ссылки на номера строк ниже относятся к исходному приложенному C-файлу. В текущем main.c добавлены режимы JSON и настройки выводов; это не подтверждение аппаратной работы новой сборки. Фильтр сохраняет перечисленные ограничения.

**Вывод:** BMI270 и BMM150 действительно участвуют в одном MEKF и корректируют один общий кватернион. Базовая математика согласована. Однако из файла нельзя подтвердить физическое совмещение осей, калибровку датчиков или точность на вашем QAV250. Есть недостатки обработки времени, помех и ошибок, перечисленные ниже.

## 1. Что уже сделано правильно

| Часть | Что делает код | Результат проверки |
|---|---|---|
| Гироскоп BMI270 | `mekf_predict()`, строки 625–741; перевод °/с в рад/с | Предсказывает общий q с правым умножением на dq |
| Акселерометр BMI270 | `mekf_update_accel()`, строки 1029–1057 | Корректирует направление опорного вектора +Z |
| Магнитометр BMM150 | `mekf_update_mag()`, строки 1067–1094 | Корректирует тот же q относительно начального магнитного поля |
| Общая ориентация | `ekf.q = [w,x,y,z]` | Body → world, одна ориентация для всех датчиков |
| Обратное преобразование | `world_to_body()` | Используется Rᵀ, согласованно с `body_to_world()` |
| Ошибка ориентации | `q_true = q ⊗ δq` | F с блоками −skew(ω) и −I, H = [skew(h), 0] имеют согласованные знаки |
| Ковариация | Joseph update, симметризация | Хорошая основа для численной устойчивости |
| Масштабирование BMI270 | ±2g: 16384 LSB/g; ±2000 °/с: 2000/32768 | Соответствует установленным в файле диапазонам |
| Начальный gyro bias | Среднее 200 выборок | Разумно при неподвижном датчике; неподвижность сейчас не проверяется |

**9 DOF здесь — 3 ACC + 3 GYRO + 3 MAG, то есть девять измерительных каналов.** Номинальное состояние содержит кватернион и три gyro bias. Ошибочное состояние — `[δθx, δθy, δθz, δbx, δby, δbz]`, поэтому P размером 6×6 — правильно. Кватернион имеет четыре компоненты, но три независимые вращательные степени свободы.

Фильтр не оценивает координаты, скорость полёта, высоту или RPM моторов. Моторы в панели — части модели, а не измеренные исполнительные механизмы.

## 2. Общая transformation matrix

Для q = [w,x,y,z] код использует:

```text
R_BW = [ 1−2(y²+z²)   2(xy−zw)      2(xz+yw)   ]
       [ 2(xy+zw)     1−2(x²+z²)    2(yz−xw)   ]
       [ 2(xz−yw)     2(yz+xw)      1−2(x²+y²) ]

v_world = R_BW · v_body
v_body  = R_BWᵀ · v_world
```

В коде эта матрица вычисляется внутри двух функций, а не хранится одним массивом. Это нормально: оба вычисления опираются на один и тот же `ekf.q`.

Но до применения общей R нужно привести измерения разных микросхем к одной системе корпуса:

```text
a_B = R_BA · calibrated_accel_A
ω_B = R_BG · calibrated_gyro_G
m_B = R_BM · S_M · (m_M − b_M)
```

Здесь R_BM — поворот установки BMM150, b_M — hard-iron смещение, S_M — soft-iron коррекция. Для BMI270 ACC/GYRO обычно имеют общую систему микросхемы; положение всей платы относительно рамы всё равно требует учёта.

Сейчас **body = оси BMI270**, а `remap_mag_axes()` задаёт R_BM = I. Это верно только при соответствующей установке датчиков. Направления осей на платах нельзя восстановить из этого C-файла. Для конкретной матрицы нужны фото установки/маркировки осей или известные повороты плат. Матрица физического поворота должна удовлетворять RᵀR = I и det(R) = +1. Произвольная смена знака одной оси создаёт отражение, а не обычный поворот.

В HTML принята система модели **X вперёд, Y влево, Z вверх**. Она совпадёт с движением реальной рамы, только если body прошивки приведена к этой системе. R в панели и поворот всех вершин 3D-модели вычисляются из одного q. Экранная камера меняет только ракурс просмотра.

Однородную матрицу 4×4 можно представить как `T_BW = [[R_BW, 0],[0,0,0,1]]`. Нулевой перенос означает закреплённую визуальную модель; он не является оценкой положения коптера. Для самой ориентации достаточно R 3×3.

## 3. Что нужно исправить или проверить

### Высокий приоритет

**1. Совмещение осей и реальная калибровка MAG отсутствуют.**

Строки 79–85, 1102–1140: offsets равны 0, scales равны 1, remap тождественный. Компенсация Bosch учитывает параметры микросхемы, но не заменяет калибровку магнитного окружения вашей сборки. Трёх scales достаточно лишь для диагональной модели; общий soft-iron требует матрицы 3×3. Применяйте калибровку в той системе, в которой она получена, и затем поворот установки.

**2. Интервал времени может не соответствовать измерениям.**

Строки 1736–1806: dt вычисляется по FreeRTOS ticks. Разрешение зависит от CONFIG_FREERTOS_HZ. При `dt > 50 ms` код подставляет 10 ms — реальный разрыв скрывается. Например, поворот во время паузы 100 ms не эквивалентен 10 ms.

Рекомендуется использовать аппаратное время BMI270/FIFO либо, для первого улучшения, `esp_timer_get_time()` на последовательных успешных чтениях. Последнее измеряет время хост-чтения, а не точный момент выборки сенсора. Для долгого разрыва нужен явно заданный режим восстановления и рост неопределённости; интегрирование одного последнего gyro через весь разрыв также не восстанавливает потерянное движение. Полезно отдельно считать пропуски/переполнение FIFO. См. [ESP Timer](https://docs.espressif.com/projects/esp-idf/en/stable/esp32s3/api-reference/system/esp_timer.html).

**3. Норма ACC не отделяет гравитационную составляющую от движения.**

Строки 1035–1040: допускается 0.8–1.2g. В тесте вектор `[0.5,0,1] g` имеет норму 1.118g и принимается, хотя содержит горизонтальное ускорение. Фильтр может интерпретировать его как наклон примерно 26.6°. Нужны проверка инновации и адаптация R под динамику/вибрации. Даже это не гарантирует разделения длительного ускорения и наклона без дополнительной информации.

**4. Норма MAG не защищает от изменения направления помехой.**

Строки 1085–1088: проверяется только отношение норм 0.6–1.4. В тесте замена `[24,0,−39]` на `[0,24,−39] µT` проходит: длина та же, направление другое. Добавьте проверку угловой инновации/NIS, контроль качества поля и поведение при отказе MAG. Помехи MAG в текущей полной векторной коррекции могут воздействовать не только на yaw, но и на roll/pitch.

### Средний приоритет

**5. Успешное чтение не доказывает свежесть и корректность BMM150.**

Строки 1146–1172 проверяют только статус возврата API. В прикладном коде нет явного DRDY, проверки non-finite и обработки overflow-значений, зависящих от версии/режима Bosch API. Особенно важно не включать недействительные выборки в начальное среднее поля. Проверьте поведение именно подключённого драйвера, чтение свежего набора и единицы данных. Контракт `bmm150_read_mag_data()` описывает компенсированные значения в µT; float/int режим задаётся макросом драйвера. См. [официальный API Bosch](https://github.com/boschsensortec/BMM150-Sensor-API/blob/master/bmm150.h).

`MAG_DIVIDER = 10` задаёт опрос примерно 10 Hz при фактической обработке IMU 100 Hz. Это не явная настройка ODR магнитометра: ODR/repetitions выбираются внутри preset вашего драйвера. В отчёте не предполагается конкретное значение ODR без приложенных исходников этой версии.

**6. Инициализация может зависнуть или запомнить неверную опору.**

Циклы калибровки на строках 1577 и 1667 не имеют timeout. Движение в процессе усреднения gyro не отбрасывается. Между усреднением ACC/GYRO и MAG проходит время; изменение положения нарушит согласованность начальных опор. Нужны timeout, проверка разброса/скорости, норма ACC и информативное состояние ошибки. Суммарная процедура — примерно 2 секунды IMU плюс около 1 секунды MAG при штатных чтениях.

**7. Reset covariance после инъекции ошибки пропущен.**

В `mekf_vector_update()` выполняются инъекция q и Joseph update P, но отсутствует перенос P в новую касательную систему ошибки. Для локальной правой ошибки первое приближение:

```c
G = diag(I3 - 0.5f * skew(delta_theta), I3);
P = G * P_joseph * transpose(G);
```

При очень малых поправках G≈I — распространённое приближение, поэтому отсутствие reset не означает, что весь фильтр неверен. Но при заметных коррекциях это источник дополнительной погрешности. При больших ошибках также стоит применять экспоненту вращения вместо нормализации `[1, δθ/2]`. Вывод reset Jacobian приведён у [Solà, раздел о сбросе локальной ошибки](https://arxiv.org/abs/1711.02508).

**8. Шумовые параметры и режимы — стартовые значения, не настройка для QAV250.**

`gyro_process_noise * dt` и `bias_process_noise * dt` корректны как приближение первого порядка, если константы — непрерывные плотности ковариации в согласованных единицах. Это не просто дисперсия одного сырого отсчёта. Параметры измерений 0.02 и 0.05 относятся к нормированным направлениям, не к g² или µT². Нужны записи реальных стационарных данных и данных с работающими моторами для обоснования параметров.

±2g и обработка 100 Hz могут быть достаточны для стендового просмотра, но насыщение ACC и недоучёт быстрых колебаний нужно проверять на фактической динамике рамы. Печать и I²C выполняются в той же задаче; таймаут I²C до 1000 ms способен надолго задержать обновление. Частоты задаются через счётчик успешных обработок, поэтому сами по себе макросы не гарантируют 100/10 Hz на реальном устройстве.

**9. Защита от NaN и состояния датчиков недостаточна.**

Сравнение `n < epsilon` не отклоняет NaN. После попадания NaN в q/P фильтр может остаться неработоспособным. Нужны `isfinite()` для входов и состояния, контроль норм q, диагностика I²C и определённое восстановление. В HTML такие пакеты отклоняются; это защищает отображение, но не исправляет прошивку.

## 4. Направление Z и магнитный курс

В `gravity_world = [0,0,+1]` опорный вектор соответствует показанию акселерометра в покое при body-Z вверх. Физическое гравитационное ускорение в системе Z-up направлено вниз; акселерометр в покое измеряет противоположную удельную силу. Название `gravity_world` здесь упрощено, но согласованные формулы инициализации и коррекции сами по себе не требуют смены знака. Нельзя заменить его на −1 без изменения всей конвенции.

Yaw устанавливается в 0 при запуске, а `mag_ref_world` строится из стартового измерения. Поэтому BMM150 стабилизирует **относительный курс от старта**, а не курс на магнитный или истинный север. Для абсолютного курса нужны иная инициализация мировой опоры, выбранная система ENU/NED и, для истинного севера, магнитное склонение.

В текущий комплект добавлены драйверы и конфигурация, оба режима прошивки успешно собраны на ESP-IDF 5.4.1: [актуальные результаты](VALIDATION.md). ## 6. Как пользоваться панелью

1. Откройте опубликованную панель отдельной вкладкой Chrome/Edge на компьютере. Она сразу запускается в явно обозначенном режиме **ДЕМО**.
2. Подключите ESP32, закройте другой Serial Monitor, выберите скорость порта, соответствующую прошивке; по умолчанию 115200.
3. Нажмите «Подключить USB» и выберите порт. Исходный C-файл уже печатает поддерживаемый формат; изменение прошивки для первого подключения не требуется.
4. Дождитесь завершения инициализации. Реальные пакеты появятся с меткой USB LIVE. При потере потока показывается последнее положение и предупреждение; перехода на демоданные нет.
5. «Датчики» показывает ACC/GYRO/MAG, «Углы EKF» — roll/pitch/yaw. Окно 10/30/60 секунд, CSV выгружает накопленный буфер не более 60 секунд. Пауза замораживает отображение, приём продолжается.
6. Журнал можно открыть в разделе подключения. Это статический просмотр: для старого текстового формата без timestamps временная шкала условно 100 ms между пакетами. Для JSONL используются timestamps устройства. Повреждённые записи пропускаются с увеличением счётчика ошибок.

Панель различает частоту приёма пакетов, переданный dt фильтра и возраст последнего приёма. В исходной прошивке графики получают около 10 Hz даже при IMU 100 Hz. По этим данным нельзя восстановить быстрые изменения между отправленными пакетами. Вычисление 1/dt не доказывает реальную стабильную частоту IMU, особенно при подмене dt в исходном коде.

В комплекте репозитория HTML, CSS и JavaScript находятся отдельно в `web/`. Из корня проекта запустите `python scripts/serve_dashboard.py` и откройте `http://localhost:8000/` в Chrome/Edge. Переносите всю папку `web`, не один HTML. CDN не нужны; телеметрия обрабатывается в браузере. Требования описаны в [документации Chrome Web Serial](https://developer.chrome.com/docs/capabilities/serial).

## 7. JSON-телеметрия в текущем main.c

Ранее подготовленный `main_json_telemetry.c` включён в основной `apps/i2c_imu/main/main.c` с двумя режимами вывода. По умолчанию передаются сырые каналы для AHRS браузера. Для вывода кватерниона выберите `QAV250 → Serial telemetry format → Firmware MEKF JSON`. Не добавляйте второй `app_main` в сборку. Эти изменения не являются полным исправлением MEKF.

Что добавлено:

- q передаётся напрямую с точностью 7 знаков, без восстановления из округлённых углов.
- `t_us` — время завершения чтения IMU по `esp_timer_get_time()`, а не аппаратный sensor timestamp.
- `seq` увеличивается для каждого отправленного пакета.
- `mag_age_ms` — время с последнего успешного чтения BMM150 API, а не доказанный возраст физической выборки. DRDY по-прежнему требует доработки.
- Перед печатью проверяется конечность чисел, чтобы не формировать невалидный JSON.
- ACC — g, GYRO/BIAS — °/с, MAG — µT согласно контракту Bosch API.

Частота вывода оставлена около 10 Hz. При увеличении частоты проверьте пропускную способность и время блокировки: UART 115200 в режиме 8N1 передаёт максимум около 11520 байт/с до накладных расходов. Длинный JSON на 50–100 Hz может не помещаться. Для высокой частоты нужны согласованная скорость обоих концов и неблокирующая/буферизованная телеметрия.

Компонент `esp_timer` уже включён в CMakeLists.txt этого комплекта. Форматирующий C-блок отдельно скомпилирован с `-Wall -Wextra -Werror`, его результат проверен как JSON. Полная сборка обоих режимов на ESP-IDF 5.4.1 подтверждена в [проверке комплекта](VALIDATION.md); аппаратная проверка остаётся необходимой.

Следующий предметный шаг для завершения аппаратной проверки: определить фактическое положение осей BMI270/BMM150 на раме, получить калибровку MAG и записать реальные timestamps и показания при известных поворотах.
